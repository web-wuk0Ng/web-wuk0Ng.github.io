part4对话agent方案设计与源码分析

agent 大模型
记录
发布日期:   2026-08-19

前置准备——对话的需求、场景、价值分析

前面做的是一个rag，这里就是真正做一个agent了
一个根据知识，不确定地回答你的一个agent
背后用到的技术
1.RAG
2.prompt工程，提示词
3.多轮对话，记住上下文
4.流式输出，我们在这个让AI思考一个复杂问题的时候，是希望一下子蹦出一大段东西，还是说展现思考过程和慢慢地把答案吐出来？显然是后者
5.容错处理。也就是AI的幻觉方面，就像是我们常说的“老板的幻觉比AI还严重”。当agent在知识库里找不到答案时，会选择瞎编。但是正确的处理方式应该时说诚实告诉用户我暂时回答不了，或者换一个用户更能接受的委婉方法，而不是直接瞎编

架构设计:ReAct设计模式核心原理

ReAct：让AI边做边想。或者说一个，想，做，想的这么一个循环
大模型不善于计算，往往计算是调用工具来进行计算的

早期的ReAct是怎么实现的

早期就是解析成固定格式的字符串调用工具什么的方式

核心就是几行代码，本质上是一个while循环+字符串解析

现代ReAct是怎么实现的

Function Call（函数调用）

Function Call就是把古法ReAct标准化了–用json来统一工具的定义和调用格式。AI调用工具的时候不再输出自然语言，而是直接返回结构化的JSON

结果回传方面：工具的返回结果也按照规定的格式传回给AI

ReAct的优点

1.让AI具备了使用工具的能力

2.让AI的回答更准确、更可靠

3.具备了处理复杂多步骤任务的能力

架构设计：对话agent的核心流程解析

对话agent的核心目标是结合外部知识(RAG召回)与工具调用能力（ReAct模式），解决复杂问题

整体流程可概括为：

1.用户输入-embedding-向量数据库召回

2.构建带上下文（召回的内容）的prompt

3.ReAct模式多轮交互

4.最终输出答案

RAG召回：让agent学习外部知识

目标：从向量数据库中获取用户问题相关的上下文信息，避免大模型出现幻觉

步骤：

1.用户输入经IuputToRag Lambda Node处理，生成用于召回的字符串

2.调用Retriever组件（以Milvus数据库为例），通过Embedding将问题向量化

3.向量数据库执行相似度匹配，返回相关文档

4.结果存入map[“documents”]，作为后续prompt的上下文来源

Prompt构建：动态拼接上下文与历史对话

目标：将用户输入、rag召回内容、对话历史整合成大模型可理解的prompt。prompt构建好后，将prompt移交给ReAct组件使用

ReAct模式：让Agent学会“思考-行动-观察”循环

目标：通过多轮工具调用解决复杂问题，核心是“显式思考-工具调用-结果观察”

关键组件深析

Lambda Node：数据流转的”转换器”：

  • InputToRag：
    • 输入：用户原始问题（可自定义预处理，如过滤无关信息）。
    • 输出：用于RAG召回的字符串（直接影响召回精度，需确保与向量数据库存储内容匹配）。
  • InputToChat：
    • 输入：用户问题+对话历史。
    • 输出：map结构（含 content / history 等key），作为 ChatTemplate 的动态参数来源。

Retriever：向量召回的 “连接器” 以 Milvus 实现为例，Retrieve 方法核心逻辑：

Tool:Agent的“双手”

Tool本质是带描述的函数，需明确告诉大模型

  • 函数名称（如：“查询当前时间”）
  • 入参/返参格式（json来描述）
  • 使用场景（如“当问题设计当前时间时调用”）

流程梳理

对话Agent的核心目标时结合外部知识（RAG召回）与工具调用能力（ReAct模式），解决复杂问题

整体流程可以概括为：

1.用户输入-embedding-向量数据库召回

2.将召回内容作为上下文注入prompt

3.LangGraph ReAct模式多轮工具调用

4.流式输出最终答案

实战

消息召回：

召回通过 retrieve_knowledge 工具实现，Agent 在推理时会自动判断是否需要调用该工具检索知识库。工具内部通过 VectorStoreManager.similarity_search 完成向量检索，详见 RAG 召回章节

构建prompt

系统提示词在_build_system_prompt中构建，描述Agent的角色定位和行为准则。与工具序列无关–LangChain框架会自动将工具信息传递给大模型，prompt中无需手动列举

历史会话由LangGraph的MemorySaver checkpointer自动管理，每次调用时传入相同的thread_id(即session_id)即可自动携带上下文，无需手动拼接历史消息到prompt

创建ReAct Agent

使用LangChain的Create_agent创建Agent,绑定ChatQwen模型、工具列表和MemorySaver检查点。MCP工具（腾讯云CLS日志、监控告警登）在首次请求时异步加载，与本地工具合并后一起绑定

执行ReAct Agent

非流式调用

调用agent.ainvoke，等待Agent完成全部推理和工具调用后一次性返回结果：

流式调用：

调用agent.astream，使用stream_mode=”messages”逐token输出，配合FastAPI的SSE接口实时推送给前端

SSE接口层

chat_stream接口将query_stream产生的时间包装成SSE格式推送给客户端，不同类型的事件对应不同的前端展示逻辑

总结

至此，对话 Agent 的核心流程 ——RAG 召回与 ReAct 模式的代码就讲完了。框架帮我们做了很多事情：LangChain 负责工具绑定与调用，LangGraph 负责多轮推理的状态流转，MemorySaver 负责会话历史管理。核心是要搞懂设计原理：RAG 补充外部知识，ReAct 让模型具备多步骤工具调用能力

请求方法：POST /api/chat_stream

请求字段

字段名 类型 描述

字段名 类型 描述

SSE响应格式：

event 类型 含义
connected 代表连接建立成功
message 回复的文本片段，会多次发送
error 连接异常，断开连接
done 消息推送完毕，断开连接

示例

快速对话接口的核心实现

  1. 接收请求，取出 id（session_id）和 question
  2. 调用 rag_agent_service.query 执行 Agent 推理，thread_id 即 session_id
  3. LangGraph MemorySaver 自动完成历史消息的读取与写入，无需手动管理
  4. 返回答案

query 方法内部将系统提示 + 用户问题包装成消息列表，通过 agent.ainvoke 执行完整的 ReAct 推理链，并从最后一条消息中取出答案。thread_id 与 MemorySaver 配合，让相同 id 的请求自动携带历史上下文：

会话历史的消息裁剪由 trim_messages_middleware 节点负责，策略是保留第一条系统消息 + 最近 6 条消息（约 3 轮对话），防止多轮对话超出大模型的上下文窗口：

流式对话接口的核心实现

SSE返回的消息event类型：

event 类型 含义
message (type=content) 回复的文本片段，会多次发送
message (type=tool_call) 工具调用状态通知
message (type=done) 消息推送完毕
message (type=error) 发生异常
  1. 流式对话的核心是 SSE，FastAPI 通过 EventSourceResponse 实现，无需手动设置 HTTP 头
  2. Agent 使用 agent.astream 的 stream_mode="messages" 模式，逐 token 产生输出
  3. 每次从流中读到文本内容，就通过 SSE 发送给客户端

query_stream 方法使用 agent.astream 的 stream_mode="messages" 模式，每个 token 触发一次回调，从 content_blocks 中提取文本块后 yield 给上层
